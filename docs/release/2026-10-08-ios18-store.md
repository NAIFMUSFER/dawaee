# App Store update from the approved iOS 18 baseline

The owner approved the user experience of 1.0.1 (18), stopped the version 19
rollout, chose public App Store review, and chose adding Sign in with Apple
beside Google. PR #74 stays draft. This separate release starts at the exact
build 18 source, `684878a78d6c6759ceb849ac4872855790766638`.

## What changes

Build 18 used `ios-auth-preview`, pointing at the isolated preview API. Public
release uses the production API, `https://dawaee-api.onrender.com`. Apple build
numbers cannot be reused: the next archive is 1.0.1 (20), based on the approved
18 application, with Apple authentication added. A source comparison showed
that 19 changed only the build counter and release documentation; it did not
introduce a different application implementation. The reported notification
registration failure therefore still requires a real production iPhone test.

The native Apple button appears beside Google on iOS sign-in and sign-up when
both the native capability and API configuration are available. Apple private
relay is accepted, and phone entry is optional in Settings. The API exchanges
a one-use Apple code, verifies Apple's signature, issuer, bundle audience,
expiry and SHA-256 nonce, and creates its own ordinary session. Provider
refresh tokens are not persisted or returned to the app. Subjects are stable;
an email match never silently attaches an Apple identity to an existing account.

Deletion requires a fresh proof from the same Apple account. Its Apple grant
is revoked before the existing fourteen-day deletion request is committed.
Revocation failures leave the deletion uncommitted. A fresh Apple sign-in can
reach the existing recovery screen during that window.

## Server preparation

Pending production migrations are 0101, 0102 and 0103. Follow
`docs/PRODUCTION-RELEASE-RUNBOOK.md`: fresh private encrypted backup, isolated
restore, exact candidate upgrade under the real restricted roles, old/new
runtime compatibility, required CI checks, then worker and API deployment.
The earlier rehearsal covered only 0101 and 0102, not the new 0103.

Set all four API-only secret settings together, without printing their values:

- `APPLE_AUTH_CLIENT_ID`: `app.dawaee.mobile`
- `APPLE_AUTH_TEAM_ID`: the existing Apple developer team ID
- `APPLE_AUTH_KEY_ID`: an Apple Sign in with Apple signing key ID
- `APPLE_AUTH_PRIVATE_KEY`: its ES256 PKCS#8 private key (secret; never committed)

Enable Sign in with Apple for the existing App ID and update its provisioning
profile. First inspect whether a suitable existing key is available. Creating
a new security-sensitive key or expanding its access requires action-time
confirmation in the browser. No signing key was created in this preparation.
The Apple Developer login did not complete; do not claim provider setup or
public submission succeeded.
