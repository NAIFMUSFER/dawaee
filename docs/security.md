# Security model

## Threat model

The assumption throughout: **application code will have bugs**. Every control
below is designed so that a mistake in one layer is caught by another, rather
than becoming a disclosure of someone's medication list.

The data here is sensitive in a specific way. A medication list is a health
record; even the *existence* of an account is health-adjacent, which is why the
OTP endpoint returns an identical response whether or not the number is known.

## Layers

### 1. Row-level security

The API connects as `dawaee_app`, a role that owns nothing and carries
`NOBYPASSRLS`. Every request-scoped query runs inside a transaction that has
set `app.user_id` via `set_config(..., is_local => true)` — transaction-scoped,
so a pooled connection never carries one user's identity into another user's
request.

Policies are written against three `SECURITY DEFINER` predicates
(`app.owns_profile`, `app.caregives_profile`, `app.has_permission`), each with a
pinned `search_path` to defeat search-path hijacking.

`db/seed/rls_probe.sql` attacks this from every direction the API exposes and
asserts 30 outcomes. CI fails the build on a single `FAIL` line.

### 2. Application authorization

`packages/core/authorization.ts` — pure functions, 21 tests. Owners hold every
permission implicitly; caregivers hold only what was granted, only while the
relationship is `active`.

One deliberate asymmetry: a caller with **no** access to a profile gets `404`,
not `403`. Returning `403` would confirm the profile exists, turning the API
into an oracle for "is this person a Dawaee user". A connected caregiver who
merely lacks one permission gets `403`, because they already know the profile
exists.

### 3. Caregiver privilege guard

RLS `WITH CHECK` sees only the new row, so it cannot distinguish "accepting an
invitation" from "adding `edit_medication` to my own permissions". A
`BEFORE UPDATE` trigger compares OLD and NEW and permits a caregiver exactly
one self-service action: leaving the circle.

The trigger is deliberately `SECURITY INVOKER` — it needs the real
`current_user` to tell a direct request-role update from one made inside an
audited definer function. A definer trigger would always report its own owner
and the distinction would collapse.

### 4. Structural integrity

A trigger asserts that every schedule, dose, stock row and refill carries the
same `patient_profile_id` as its parent medication. Cross-profile contamination
is impossible, not merely unlikely.

## Authentication

- **Phone OTP.** Codes are stored only as SHA-256 hashes, in a table the
  request-serving role **cannot read at all**. Issue and verify go through
  `SECURITY DEFINER` functions, which also makes the rate limit and the attempt
  counter atomic across every API instance rather than racy per-process checks.
- **Access tokens** are short-lived HS256 JWTs. The session row is checked on
  every request, so "sign out everywhere" takes effect immediately rather than
  when a token happens to expire.
- **Refresh tokens** are opaque, stored hashed, and rotated on every use.
  Presenting an already-rotated token is treated as theft: every session on that
  device is revoked.

> Both of the last two controls were *broken* in the first implementation — the
> counter increment and the theft revocation were being rolled back by the
> `throw` that followed them. See [findings.md](findings.md).

## Uploads

Applied in order:

1. Declared content type must be an allowed image type.
2. Declared size must be within the cap (15 MB default).
3. The object key is **generated by the server**; the client's filename is never
   used, so a crafted name cannot traverse or collide.
4. On the bytes themselves, a magic-byte sniff must agree with the declared
   type. This is what rejects a renamed script or a polyglot file.
5. Private bucket, short-lived signed URLs for both upload and read.

## Secrets and logging

- No secret is committed. `render.yaml` marks every one `sync: false`.
- Production boot **refuses to start** on `OTP_DEBUG_ECHO=true`, a default
  `IP_HASH_SALT`, a short `JWT_SECRET`, or `STORAGE_PROVIDER=local`.
- IP addresses are stored only as salted hashes.
- Log redaction is enforced in the logger, not left to call sites: medication
  names, phone numbers, allergies and tokens are censored centrally, because one
  careless `log.info({ medication })` would otherwise leak health data into an
  aggregator forever.
- The admin surface exposes system health and delivery failures, and **no**
  medical data. An operator debugging a failed WhatsApp send does not need to
  know what the medication was.

## Audit

`audit_logs` is append-only: `UPDATE`/`DELETE`/`TRUNCATE` revoked from both
application roles, plus a trigger that raises regardless of grants. Entries are
written in the same transaction as the change they describe, so the log and the
data cannot disagree. Values are scrubbed of tokens and hashes before storage.

## What is NOT claimed

- **No compliance certification.** The architecture was built with Saudi PDPL
  principles in mind — consent, data access, export, deletion, purpose
  limitation — but no formal assessment has been performed and none is implied.
- **No penetration test** has been run against a deployed instance.
- **No HIPAA/GDPR attestation.**

These require formal validation by qualified assessors, not a codebase that
looks careful.
