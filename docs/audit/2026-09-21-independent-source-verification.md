## 3. الاختبارات الجديدة والقياس قبل الإصلاح

بيئة التنفيذ Node 22.23.2، npm 10.9.7، Vitest 2.1.9. شُغّل إعداد Vitest الأصلي، بما فيه globalSetup وبناء الويب. جرى تطبيق ملفات الترحيل الـ95 الأصلية في قاعدة PGlite مع أدوار app/worker ومُرحّل NOSUPERUSER/NOBYPASSRLS. هذا يختبر SQL وRLS في هذه البيئة، **ولا يحل محل PostgreSQL 16 و17 أو اختبار سباق اتصالات فعلية**.

اختبارات المرحلة 2 تتعمد التعبير عن السلوك الآمن المتوقع، ولذلك تبقى حمراء على مصدر الأساس. لا تغيير runtime ولا تعديل migration مطبق لإمرارها. ملفاتها:

- `apps/api/test/independent-audit-db.ts`: قاعدة اصطناعية وأدوار وترحيلات فعلية.
- `apps/api/test/independent-audit-f1.test.ts`: اختبار واحد؛ فشل قبل الإصلاح. statuses=[200,409]، cancel=1، purge=1، destroy key=1، queue=0، signedIn=false بعد ضياع الرد. لا تُسجل tokens أو بيانات مرضى.
- `apps/api/test/independent-audit-f5.test.ts`: اختباران؛ فشلا قبل الإصلاح، بقياسات الجدول الفعلي المبينة أدناه.
- `apps/api/test/independent-audit-f16.test.ts`: اختباران؛ housekeeping نجح، materialize فشل قبل الإصلاح. تجريب rule بلا times لم يسبب الاستثناء المفترض؛ الحالة المثبتة هي عنصر null داخل times. لم تُعطّل قيود SQL لإنتاجها.

## 5. قرارات F12 وF13 قبل التنفيذ

**F12:** تجاهل quiet hours يخرق تفضيل المرافق وقد يرسل محتوى في وقت غير مناسب. إسقاط التنبيه نهائيًا يبقي المرافق بلا متابعة. الخيار الأكثر أمانًا المقترح هو حفظ نية متابعة عامة مؤجلة لنهاية الهدوء، ثم إعادة فحص حالة الجرعة والصلاحيات والمستلم قبل إرسالها؛ لا نصائح تعويض جرعة ولا إرسال لمن سُحبت صلاحياته. يُختبر التأكيد/التخطي/الإلغاء أثناء التأجيل وعدم التكرار. هذا قرار برمجي لم يُنفذ بعد ولا يثبت وصولًا على جهاز.

**F13:** الاعتماد على takenAt يحفظ زمن التناول لكنه قد يجعل نافذة التراجع منتهية لحظة المزامنة. السماح بزمن غير محدود يوسع التعديل التاريخي. الاختيار هو 10 دقائق من **وقت قبول التأكيد في الخادم**، مع إبقاء takenAt لوقت التناول وعدم تغيير حساب المخزون/الأحداث أو صلاحية الفاعل. يلزم حدث/حقل موثوق من الخادم؛ أي مخطط إضافي بترحيل جديد فقط.

## 6. ترتيب العمل وحدود النشر

بعد توثيق هذه المرحلة، تُنفذ المرحلة 3 للقراءة فقط ثم الإصلاح بالتسلسل: P0 (F1، F3، F2، الجزء المثبت من F16)، ثم P1 المذكورة والنتائج الجديدة المؤكدة، ثم P2. لكل بند فرع من المرشح، اختبار أحمر قبل التغيير وأخضر بعده، commit واضح وPR مستقل. هذا الفرع فرع **أدلة واختبارات قبل الإصلاح**، وليس release صالحًا للنشر، ولا يجوز إضعاف اختبارات الرفض لإمرار F1.

لكل إصلاح: المجموعة الكاملة Vitest/eslint/typecheck للخادم والجوال، مسبار RLS، وترحيلات مرتين على قاعدة نظيفة؛ وبوابة CI/أمان PG16/17 للـcommit نفسه. ما يتعذر يُذكر بدل استبداله بادعاء نجاح. الإنتاج يتطلب المعاينة للـcommit نفسه ورحلات تحقق، backup حديثًا مؤكدًا قبل migration، rollback مكتوبًا ومجربًا، والعامل قبل API على commit واحد، وتوافق build6/upgrade_required. نقص بوابة يمنع نشر الإنتاج ولا يوقف البنود الأخرى.

**حالة التنفيذ عند كتابة الوثيقة:** مكتوب: اختبارات الإثبات وهذه المطابقة؛ مختبَر: الحالات المحددة أعلاه؛ إصلاح runtime: لا؛ منشور للمعاينة: لا؛ منشور للإنتاج: لا؛ مجرّب على جهاز: لا. الآثار الخارجية حتى الآن: قراءة Git/GitHub وتنزيل اعتماديات واستعلام advisory؛ لا تعديل خدمات أو قواعد منشورة ولا إنشاء حسابات أو إرسال رسائل.
