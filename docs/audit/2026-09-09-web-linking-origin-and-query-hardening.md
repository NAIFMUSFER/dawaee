# Web Linking boundary, query fidelity, CSP hash, and generated-source evidence

Baseline: `7ba475365ba64f8ef24eff1fd9787101b06c772b` on Draft PR #14. No merge,
deployment, production mutation, workflow-permission change, scanner exclusion or
alert dismissal is part of this correction.

## Proven defects

The committed web artifact is generated by `scripts/build-web.sh` from the Expo
web export and copied into the production Docker image. The generated entry at
the baseline contains both Expo Linking web `message` listeners without an
`event.origin` check. A cross-origin window that retains an opener reference can
therefore synthesize a Linking signal. The handler re-reads the victim's current
`window.location.href`, so the sender cannot directly choose the URL; the proven
boundary defect is the unauthenticated cross-origin signal, not arbitrary URL
injection. The prior CodeQL SARIF independently reports two
`js/missing-origin-check` findings at the generated document.

The same generated dependency code wraps `URLSearchParams.set()` with
`encodeURIComponent()` and applies `decodeURIComponent()` to values already
returned decoded by `URLSearchParams`. A literal value such as `100% /` does not
round-trip, and a literal `%2F` is changed to `/`. The prior SARIF reports an
`js/incomplete-sanitization` finding on this generated path.

Separately, `apps/api/src/routes/web-app.ts` derives the CSP by matching
executable HTML with `<script>(...)</script>` regex. CodeQL reports
`js/bad-tag-filter` on that parser. The build has the exact inline script before
HTML is emitted, so reparsing HTML at runtime is unnecessary.

Finally, `apps/api/public/` was checked in even though Docker regenerates it from
source. `apps/api/test/web-app.test.ts` therefore exercised a repository snapshot
rather than proving the current source build. This creates evidence drift: a
stale generated artifact can be scanned/tested while production compiles a
newer one.

## Bounded remediation

`scripts/inline-web.py` hardens the four exact dependency snippets at the
production bundling boundary. Each replacement requires exactly one match and
fails the build with `web hardening drift` if an Expo upgrade changes the
expected code. Both Linking message listeners now accept only
`event.origin === window.location.origin`. The redundant query encode/decode
layers are removed; native `URLSearchParams` behavior remains.

The bundler also computes SHA-256 over the exact inline script body and emits a
base64 sidecar. `web-app.ts` validates that sidecar as exactly 32 decoded bytes
and builds CSP from it. The HTML tag regex and runtime script parsing are gone.
A missing or malformed sidecar fails route registration rather than silently
weakening CSP.

Generated `apps/api/public/` output is removed from version control and ignored.
The web route test now runs the same `scripts/build-web.sh` used by the Docker
build before starting its harness, so the test proves current source rather than
a stale artifact.

## Regression proof

`apps/api/test/web-build-hardening.test.ts` drives the real Python bundler against
a synthetic Expo-like export and executes the transformed JavaScript. It proves
cross-origin messages are ignored, same-origin messages still fire, `100% /`
round-trips through `URLSearchParams`, literal `%2F` is preserved, and the
sidecar equals SHA-256 of the exact emitted script. A dependency-shape mutant
proves the hardener fails closed instead of silently skipping a replacement.

`apps/api/test/web-app.test.ts` rebuilds the current production web source and
asserts that the response CSP contains exactly the build-emitted script hash.
The existing routing/cache/same-origin assertions remain.

This is not a dependency fork or a generic JavaScript sanitizer. It is a narrow,
version-pinned build boundary around four proven snippets. An Expo upgrade must
make the regression test and fail-closed replacement contract pass before the
hardening can be changed.
